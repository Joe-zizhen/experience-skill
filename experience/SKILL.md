# experience — 经验固化与检索

第一性原理：agent 的记忆 = 当前上下文窗口，窗口外的一切对它不存在。所以"agent 拥有经验"只有一个物理含义——相关 token 在它做决策的那一刻位于窗口内。文件只是存储，**存储不是经验，检索才是**。本 skill 因此只做三件事：写入（付出代价的当场固化）、检索（决策点之前把索引灌进上下文）、保鲜（条目带死因，过期即杀）。

**定位边界：本系统管记忆，不管方法论。** 它让 agent 不再重复踩已记录的坑；"不探根因、在问题处打补丁、不顾全局"这类行为问题属于推理习惯，由编码行为准则负责（如 senior-engineer skill 的编码红线/行为铁律/对抗性审查，或项目内的等效落地文档），不在本 skill 射程内——对这一点抱有错误期待会导致对本系统的误判。

## 红线（不可违反）

1. **先读索引再动手。** 每次任务——包括探索代码、回答问题、写代码之前——必须先读项目的 `docs/experience/INDEX.md` **和**本 skill 目录下的 `general.md`（两者都读：项目库管项目特定经验，general 管跨项目通用坑；哪个不存在就跳过哪个）。命中索引行就打开对应条目，写代码前遵循它。
2. **不合格不入库。** 一条信息必须同时通过下方"入库四问"才准写入。"本次做了什么""任务顺利完成"一律拒收——那是流水账，可从 git log 和当前代码免费重导，阅读成本为正、价值为零。
3. **祈使句，写给未来的 agent。** 条目是发给未来执行者的指令（"先 X 再 Y""别做 Z"），不是写给人的日记（"上次出了什么问题"）。
4. **标题 = 触发条件 + 关键词簇。** 标题回答"我什么时候该读你"（如 `[构建] 命令行打包前（编译、assemble、APK）`），附同义词/英文/术语别名，另加 1–2 个"任务时说法"（未来用户口语化描述任务的方式）提高召回；不写内容摘要（如"gradlew 问题"）。写入时无法预知未来的检索关键词，触发条件和词簇是唯一的挂钩。
5. **每条带死因。** 写不出"什么发生后本条删除"的条目不收；读到疑似失效的条目**不当场删**——标记"疑似失效"，走自清洁人工问询（见「自清洁」节）。
6. **冲突时代码/契约赢。** 条目与当前代码或契约文档冲突，以代码/契约为准并删除该条目。经验是例外清单，不是事实权威；接口、字段、架构真相永远归代码和契约文档。
7. **永不因未命中而淘汰条目。** "最久未命中"不等于无价值（低频高价值条目正是系统要保的）。索引 ≤150 条时全平铺；超过则转两阶段索引（见「规模与分级」）。条目只有两种合法死法：自清洁确认死因达成、冲突裁决（代码赢）——且都经人工问询。
8. **项目文档自洽。** 写入 `docs/experience/` 的内容不得出现"见 experience skill"字样或 skill 安装路径——规则全文必须写在项目文档内（仓库可共享、可评审、可进 git），skill 只是执行器，在其他机器上可能不存在。
9. **人工闸门。** 入库、删除、冷藏三类变更都必须经用户确认：agent 负责发现、起草、附证据推荐；用户裁决（确认/修改/否决、删/改后冷藏/保留）。禁止静默写入或静默移除。

## 入库四问（全部答"是"才准入）

1. **会重现** —— 不是一次性事件？
2. **重导有代价** —— 从当前代码/git 不能免费重新推出？（失败路径、外部系统行为、用户的偏好决策，代码里都看不见；"做了什么"看得见，拒收）
3. **改变行动** —— 未来的 agent 读到后会做不同的事？（不改变行为的信息是噪音）
4. **写得出死因** —— 能明确说出"什么发生后本条不再成立"？

一句话：**经验 = 已付过代价、未来还要再付、且付费可避免的知识。**

## 写入触发器（事件驱动，不是仪式驱动）

只在以下事件发生的**当场**写入；任务结束不做例行总结：

- 踩坑耗时超过约 10 分钟（排查、返工、重新构建都算）；
- 发现一个难找的入口/文件/机制（且下次还要再找第二次）；
- 外部系统（后端、设备、第三方 SDK）的行为与文档不符；
- 被用户第二次纠正同一事实或偏好；
- 用户明确要求"记住这个"；
- senior-engineer 完成 mymodules 可复用模块入库时（联动写入 `[功能]` 功能经验到 project.md，同样经用户确认）。

**入库流程（人工闸门）**：触发事件 → 当场按格式起草完整条目（信息最新鲜时记录事实）→ 展示给用户并附一句入库理由 → 用户确认/修改/否决 → 确认后才写入副本并登记索引。禁止不经确认静默入库。

## 条目格式（六行封顶）

```md
## [场景] 触发条件式标题
- 行动：当<场景>时，做什么/别做什么（祈使句；**场景限定词必须有**——防止条目被错误套用到场景外；有明显易混淆的相邻场景时加一句"不适用于 Y"）
- 根因：一句话说清为什么（没有根因的坑会换个形态再踩；**实测根因直接写，推断的根因必须标注"（推断）"**——错误根因比没根因更危险，标注给未来留验证入口）
- 证据：指向任务证据/契约/代码位置（docs/task-context/... 或 文件:行号）
- 死因：什么发生后删除本条
- 记录：<写入日期>｜最近命中：<日期，每次因本条避免踩坑即更新>（**日期一律用 `date +%F` 取系统时间，禁止凭记忆填写**）
```

"最近命中"仅供回顾参考，**不作淘汰依据**——条目永不因未命中而淘汰（见「规模与分级」）。

## 存放位置与角色分工

- **skill = 规则的权威与模板源。** 全部规则（四问、格式、自清洁、规模）以此文件为准；到新项目时由本 skill 把规则"播种"过去。
- **项目文档 = 规则的落地副本。** `docs/experience/INDEX.md` 头部携带规则全文（从本 skill 的模板拷贝），自洽运行，不引用 skill——没有装本 skill 的机器、队友、其他 agent 工具也必须能直接用。
- **项目经验** → 项目 `docs/experience/`：`INDEX.md`（总账，≤150 条全平铺）+ `pitfalls.md`（踩坑）/ `project.md`（项目入口、环境与 `[功能]` 功能经验——可复用模块的指针，由 senior-engineer 入库时联动写入）/ `code.md`（代码与协作惯例）。
- **通用经验**（跨项目：操作系统、工具链、平台级坑）→ 本 skill 目录 `general.md`，格式相同。

## 与 senior-engineer 的接缝

- senior-engineer 完成 mymodules 可复用模块入库时，联动本 skill：起草 `[功能]` 功能经验（标题 =「需要 X 时」，行动 = 复用指针），经用户确认后入项目 `project.md`。
- 本 skill 索引命中功能经验、需要复用时，必须先读 mymodules 契约页核实——经验管"记得有这个东西"，mymodules 管"这个东西的当前真相"，冲突时以 mymodules 目录为准。

## 新项目播种流程（项目还没有 docs/experience/ 时）

首次在一个没有经验库的项目触发时，按顺序执行，不得跳步：

1. **找入口**：确认该项目的"必读入口文件"（`AGENTS.md` / `CLAUDE.md` / 等效 agent 指令文件）。一个都没有时，只建经验库，并明确告知用户：需要他手动把门禁段落挂到该项目的入口文件，否则索引不会被读到。
2. **建经验库**：创建 `docs/experience/INDEX.md`（用下方模板**全文原样拷贝**，规则头部一个字不许丢）和空副本 `pitfalls.md` / `project.md` / `code.md`（各带一行头部：入库规则见 INDEX.md 头部；本副本 ≤300 行）。本次触发若带着真实条目，顺便写入对应副本和索引。
3. **挂门禁**：在入口文件加入门禁段落（模板见下）。措辞可适配项目语言，但四点语义不可丢：每次任务先读 INDEX；踩坑当场记录；冲突时代码/契约赢；每天首次 pull 后自清洁。
4. **告知用户**：经验库已建立、门禁已挂、从下个任务起自动生效。

### INDEX.md 播种模板（原样拷贝，再在其后追加条目区）

```md
# 经验总账 INDEX

> 本索引是每次任务的唯一必读入口。
> 每条一行：`[场景] 触发条件（关键词簇） → 副本文件「条目标题」`。命中当前任务即打开条目，写代码前遵循。
>
> 条目规则（缺一不入库）：会重现、重导有代价（从代码/git 不能免费推出）、改变行动、带死因。
> 写法：祈使句，写给未来的执行者；标题 = 触发条件 + 关键词簇（同义词/英文/术语别名，外加 1–2 个"任务时说法"——未来用户会怎样口语描述这个任务），不写内容摘要；条目含 行动/根因/证据/死因/记录日期/最近命中；"行动"字段必须带场景限定词（"当 X 时…"），有明显易混淆的相邻场景时加"不适用于 Y"；日期字段一律用 `date +%F` 取系统时间，禁止凭记忆填写。
> **入库问询：条目由 agent 按格式当场起草后，必须经用户确认才入库**（确认/修改/否决），禁止静默写入。
> 裁决：条目与当前代码/契约冲突时，以代码/契约为准执行——但条目不当场删，标记"疑似失效"，走自清洁问询。
> 命中标记（强制）：每次任务最终面向用户的回答文本的首行输出 `[经验门禁] 命中 N 条：标题列表 / 无命中`（工具调用和 thinking 不算回复）。
> 检索三通道：①逐行匹配下方索引行；②任务关键词明确时顺手 grep 一次 `docs/experience/` 全文兜底；③决策点重扫：任务性质转变时（探索转修 bug、写代码转构建/真机/联调），重扫下方对应场景行一次（不全文重读）。
>
> 自清洁（两个时机）：
> - 定期：每天首次 git pull 后（hook 按 `.last-clean` 提醒，完成后写入当天日期；建议把该文件加入 .gitignore）。
> - 即时：任务中命中条目但发现坑已修复 → 当场触发该条的清洁。
> 清洁流程：1. 锚点检查（证据里的代码锚点不存在 → 坑已修或场景已死）→ 2. 死因核对 → 3. 外部行为类标"待复核"，实测后处理。
> **所有移除与冷藏必须人工问询**：agent 附证据和推荐理由，用户裁决：删 / 改后冷藏 / 保留。[用户决策] 类条目永不自动处理。
>
> 冷藏区（archive.md）：只收死场景条目（功能/代码整体不存在），不因久未命中而冷藏；条目完整保留，grep 可达，场景复活时移回。
>
> 规模（永不因未命中而淘汰条目）：
> - ≤150 条：全平铺于本索引，每次任务全量读。
> - >150 条：转两阶段——本索引只列场景目录（每类一行：场景名+关键词簇+条数），命中场景后打开对应分类副本匹配条目；grep 兜底不变。
> 移除合法路径仅两条：自清洁确认死因达成；冲突裁决（代码赢）。两者都经人工问询。
>
> 本系统自身的死因（每周自清洁时用户凭命中标记印象判断）：连续 2 周零命中 → 亚健康；连续 4 周零命中或门禁成为负担 → 降级为被动文档库；连续 2 个月零命中且无新增 → 删除门禁、归档经验库。系统与条目同权：定了死因的就执行。
```

### 入口门禁标准段落（AGENTS.md / CLAUDE.md 用，可翻译适配）

```md
## 经验门禁（强制，每次任务必做）

1. 任务开始——包括探索代码、回答问题、写任何代码之前——必须先读 `docs/experience/INDEX.md`（≤150 条全平铺，全量读）。
2. 索引行命中当前任务时，打开对应副本条目，写代码前遵循它。
3. 每次任务最终面向用户的回答文本，首行输出经验命中标记：`[经验门禁] 命中 N 条：标题列表 / 无命中`（工具调用和 thinking 不算回复）。
4. 踩坑（耗时排查/返工）、发现难找的入口、外部系统行为与文档不符、被用户第二次纠正同一事实时：当场按 INDEX 头部规则**起草**条目，**经用户确认后入库**，再收尾。
5. 条目与当前代码/契约冲突时，以代码/契约为准执行；条目不当场删，标记"疑似失效"走自清洁问询。
6. 自清洁两个时机：每天首次 `git pull` 后；命中条目发现坑已修复时当场触发。所有移除/冷藏经用户裁决（规则在 INDEX.md 头部）。
```

## 宿主 hook 自检与安装（每个新宿主/新机器第一次使用时）

文本门禁是概率性的，hook 是结构强制的。换宿主或换机器后第一次使用本 skill 时执行本章节，把检索从"请求"升级为"结构"：

### 1. 识别宿主（探测不出就问用户一次，禁止瞎猜）

探测线索：系统提示自报身份、宿主配置目录存在性（`~/.kimi-code/`、`~/.claude/`、`~/.cursor/` 等）、环境变量。猜错宿主 = 写错配置，宁可问一次。

### 2. 检查是否已安装

读宿主配置文件搜 `inject-experience-index` 签名；已存在 → 跳过本章节，不重复安装。

### 3. 按宿主能力分级安装（降级链）

- **有 session-start hook 机制**（如 Kimi Code、Claude Code）：写入下方脚本模板 + 注册 hook 配置（示例见下）。
- **无 hook 但有常驻规则注入**（如 Cursor 的 `.cursor/rules/*.mdc` 且 `alwaysApply: true`）：把门禁段落写成常驻规则文件，效果等价于注入。
- **两者都没有**：只靠入口文件文本门禁（播种流程第 3 步），并明确告知用户——该宿主的经验检索是概率性的，"任务首行输出命中标记"是唯一的可观测手段。

### 4. 安装安全红线（违反可能搞挂宿主配置）

1. 改配置**前先备份**（`cp 配置 配置.bak-<日期>`）。
2. **只追加，不改已有配置**；追加处带注释标记 `# experience skill`，方便日后卸载。
3. 改完**验证语法**（TOML/JSON 能被正常解析），验证不过立即用备份回滚。
4. hook 通常**下个会话才生效**，本次会话仍靠文本门禁——必须如实告知用户，不得假装已生效。
5. hook 脚本运行时优先 node，无 node 用 python，都没有才用 shell 原语（并告知用户平台风险）。

### 5. hook 脚本模板（原样写入目标位置）

```javascript
// inject-experience-index.mjs — SessionStart hook：把项目经验索引注入 agent 上下文
// 输入：stdin JSON（含 cwd 字段）；输出：INDEX.md 全文到 stdout，exit 0
// 附加：今日未执行自清洁时（.last-clean 日期 ≠ 今天）附加一次提醒
// 日志：每次执行追加一行到脚本同目录 experience-hook.log（验证用，可删）
// 任何失败都静默 exit 0（fail-open，绝不影响主流程）
import fs from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

const scriptDir = path.dirname(fileURLToPath(import.meta.url));

function log(line) {
  try {
    fs.appendFileSync(path.join(scriptDir, 'experience-hook.log'), line + '\n');
  } catch { /* 日志失败静默 */ }
}

let input = '';
process.stdin.on('data', (c) => { input += c; });
process.stdin.on('end', () => {
  try {
    const payload = JSON.parse(input || '{}');
    const cwd = payload.cwd || process.cwd();
    const indexPath = path.join(cwd, 'docs', 'experience', 'INDEX.md');
    if (!fs.existsSync(indexPath)) {
      log(`${new Date().toISOString()} event=${payload.hook_event_name || '?'} cwd=${cwd} result=no-index`);
      process.exit(0);
    }
    const content = fs.readFileSync(indexPath, 'utf8');
    if (!content.trim()) {
      log(`${new Date().toISOString()} event=${payload.hook_event_name || '?'} cwd=${cwd} result=empty-index`);
      process.exit(0);
    }

    let cleanNote = '';
    try {
      const d = new Date();
      const today = `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}-${String(d.getDate()).padStart(2, '0')}`;
      const marker = path.join(cwd, 'docs', 'experience', '.last-clean');
      const last = fs.existsSync(marker) ? fs.readFileSync(marker, 'utf8').trim() : '';
      if (last !== today) {
        cleanNote = '\n\n[提醒] 若今天已 pull 过代码，请执行经验自清洁（约 3 分钟，规则在 INDEX 头部），完成后把今天日期写入 docs/experience/.last-clean。';
      }
    } catch { /* 提醒失败静默 */ }

    const output =
      '[经验门禁·自动注入] 以下是本项目经验索引。规则：命中当前任务的条目必须先打开遵循再动手；' +
      '任务首行输出经验命中标记（命中 N 条+标题 / 无命中）。\n\n' + content + cleanNote;
    process.stdout.write(output);
    log(`${new Date().toISOString()} event=${payload.hook_event_name || '?'} cwd=${cwd} result=injected bytes=${output.length} cleanNote=${cleanNote ? 'yes' : 'no'}`);
    process.exit(0);
  } catch (e) {
    log(`${new Date().toISOString()} error=${String((e && e.message) || e)}`);
    process.exit(0);
  }
});
```

### 6. 注册示例（两个已验证宿主）

- Kimi Code（追加到 `~/.kimi-code/config.toml`，用户级一次配置全项目生效）：

  ```toml
  [[hooks]]
  event = "SessionStart"
  command = "echo hook-fired >> <绝对路径>/.kimi-code/hooks/hook-fired.log && node <绝对路径>/.kimi-code/hooks/inject-experience-index.mjs"
  timeout = 5
  ```

  **实测教训（2026-08-19，Windows）**：`command` 里用 `~` 不会被展开，hook 静默失败（fail-open）——必须用绝对路径字面量；前置 `echo` 探针用于区分"未触发"与"执行失败"，验证通过后可去掉。

## 读取流程（每次任务开始）

0. 首次在当前宿主使用本 skill 时，先执行「宿主 hook 自检与安装」章节。
1. 读 `docs/experience/INDEX.md` 和本 skill 目录的 `general.md`（哪个不存在就跳过哪个；都不存在则跳过，不为读而创建）。
2. 逐行判断索引的触发条件与关键词簇是否命中当前任务；命中即打开对应副本条目。任务关键词明确时，顺手 `grep` 一次 `docs/experience/` 全文作兜底召回（能捞回冷藏区 `archive.md` 里的条目）。任务性质转变时（探索转修 bug、写代码转构建/真机/联调），重扫索引中对应场景行一次（不全文重读）。
3. **最终面向用户的回答文本首行输出命中标记**：`[经验门禁] 命中 N 条：标题列表 / 无命中`（工具调用和 thinking 不算回复）——让"读没读"对用户一眼可查。
4. 任务中遵循条目；发现条目疑似失效（坑已修/与代码冲突），**不当场删**——标记"疑似失效"，走自清洁人工问询。
5. 任务结束不做经验总结——只有触发器事件发生时才写。

## 自清洁（定期 + 即时两个时机）

经验不会自然淡忘，只会悄悄腐烂——同事在远端修好了坑，条目不会自己消失。

**时机**：
- **定期**：每天首次 `git pull` 后，约 3 分钟（hook 按 `.last-clean` 提醒，清洁完成后写入当天日期）。
- **即时**：任务中命中条目但发现坑已修复 → 当场触发该条的清洁，不等定期仪式。

**流程**：
1. **锚点检查（可自动）**：条目"证据"里的代码锚点（文件路径、符号名）用 grep 验证存活；锚点消失 → 打开核实，区分两种情形：坑被修了（死因达成）或场景死了（功能/代码整体不存在）。
2. **死因核对（半自动）**：读每条"死因"，本次 pull 的变更满足了它 → 列入处理候选。
3. **外部行为类**：后端/设备/第三方行为无法从代码推断，标"待复核"，下次相关任务实测后处理。
4. **用户决策类**：永不进入自动处理。

**人工闸门（强制）**：所有移除与冷藏必须问询用户——agent 附证据和推荐理由（如"场景完全死掉、代码不存在，建议删"／"场景不在但模块仍在 X 被调用，我先改写条目再放冷藏"），用户裁决：**删 / 改后冷藏（archive.md）/ 保留**。问询要低成本：给完整推荐，用户一句话即可裁决。

## 规模与分级

- **条目永不因未命中而淘汰**——"最久未命中"不等于无价值，低频高价值条目（灾难恢复、季节性联调）正是系统要保的。
- **≤150 条**：INDEX 全平铺，每次任务全量读（约 4K tokens，毫无压力）。
- **>150 条**：转两阶段索引——INDEX 只列场景目录（每类一行：场景名+关键词簇+条数），命中场景后打开对应分类副本匹配条目；grep 全文兜底通道不变。
- 每个副本 ≤300 行（约 30 条），超限按领域裂变新副本（如 `pitfalls-build.md`），INDEX 同步分区。
- 冷藏区 `archive.md`：只收死场景条目（功能/代码整体不存在，人工裁决），条目保持完整格式，grep 可达，场景复活时移回；INDEX 底部保留一行存在提示。
- **通用层 `general.md`**：单文件全平铺（≤150 条），读取只有一跳（直接 Read 全文，不经索引）；超过则拆为 `general/` 目录（INDEX + 分类文件），走与项目侧相同的两阶段逻辑。通用坑增速远慢于项目坑，拆分是很久以后的事。

## 维护（读到即执行）

- 发现条目疑似失效 → 标记"疑似失效"，走自清洁人工问询，不当场删。
- 条目帮到你 → 更新它的"最近命中"日期（仅供回顾，不作淘汰依据）。
- 副本内同类条目相邻放置；副本 ≤300 行；INDEX ≤150 条，超过转两阶段（见上）。

## 系统自身的死因

知识系统不会暴毙，只会慢性死亡成"没人敢动的遗产文档"。本系统与条目同权：说不出死因的不收，定了死因的就执行。

- **信号源** = 命中标记（用户每次任务都可见，用户即观测者，不新增统计机制）。
- **判定时机** = 每周自清洁时，用户凭印象判断一次。
- **阈值与分级处置**：
  - 连续 2 周零命中 → 亚健康：讨论条目是否脱离实际任务。
  - 连续 4 周零命中，或门禁被用户感知为负担 → 降级：砍 hook 与自清洁，只留项目 `docs/experience/` 作被动文档库。
  - 连续 2 个月零命中且无新增条目 → 死亡：删除入口门禁段落，经验库归档。
- 阈值是默认计划；真实触发器是用户体感——系统是为人服务的，不是相反。
