# senior-engineer — 编码行为、复用治理与对抗性审查

本 skill 回答一个问题：**高级工程师写代码时，有哪些不明说但都执行的规矩？** 它不编排流程，只约束编码行为本身。

规则分四级：**[INV]** 不变量（违反即缺陷——错误、安全问题、越权或证据失真，无豁免）；**[DEFAULT]** 默认策略（项目事实或用户要求可覆盖）；**[HEURISTIC]** 审查信号（只触发复核，不直接定罪）；**[EXAMPLE]** 示例（无规范效力）。

分工：本 skill 管**编码时的一切**——规范、风格、模块体系、复用检索、审查；**experience** skill 管跨会话记忆（坑/入口/用户决策/功能经验）。两者接缝见末节。

## 第一部分：编码不变量 [INV]

违反以下任何一条即缺陷，无豁免。

**1 默认过滤必须在函数签名旁披露。** 读取类函数默认隐藏了数据（软删除、禁用、归档、时间窗），要在签名旁写明「默认隐藏什么」「怎么取全量」。不披露的后果不是报错，是**静默少数据**——调用方拿到一个看起来正常的短列表，没人会去查。

**2 注释与 docstring 只描述实测成立的行为。** 写下「线程安全」「幂等」「自动重试」之前先有一次实测，拿不出实测就删掉那句。过期注释比没有注释更坏：它让下一个人跳过验证直接用。

**3 替代数据要带来源标记，标记不在层间丢失。** mock、假数据、降级返回值从产生那一刻就带上「这是替代数据」的标记，一路传到消费端，中间任何一层不许摘掉。不带标记的假数据跟真数据长得一模一样——上线那天字段对不上才发现。

**4 永久修复必须先有足以选择修复边界的因果解释。** 拿不出复现步骤的根因只是假说。活跃事故中，可逆、可观测、可快速回滚的止血（回滚、关开关、切流、隔离）可以先于根因调查——但止血不是修复，**把止血当修复交付视同违反本条**。修同一处多次仍没好 → 停手复核问题模型（错误假设、观测不足、多个独立缺陷、架构问题都是候选），与人一起定，不宣判架构错误。

**5 交付物必须完整且已验证。** 不留占位符和"rest unchanged"式的半截活；每个结论有证据（命令亲手跑过、输出实际看过）。"应该能过"不是过。

**6 测试证据不许造假。** 不许用 skip、删测试、放宽断言、mock 被测对象、`|| true`、降阈值制造绿灯。**红绿反验**（约束新增或修改的测试）：故意改一个期望或输入，确认测试变红，再改回来——没红过的测试不算测试。**禁止自证测试**：期望值不许用被测代码的同一算法/helper 计算，只能来自独立样例、固定 fixture、合同或独立 oracle。**每道防线都要证明它能拦住**：新增的每个校验/过滤/权限判断/边界守卫，逐个喂一个本该被它拦下的输入，观察它真的拦下了；做不到就删掉或改成能触发的写法——恒真守卫比没有守卫更坏。守卫的注释只许描述实测能拦下的范围。

**7 禁止把官方库源码抄进来改。** 唯一例外是官方明确以 sample/codelab 发布的参考代码且保留许可证头。引入官方或第三方依赖前要评估版本兼容、体积、许可证、维护状态和传递依赖并留证据。

## 第二部分：行为默认策略 [DEFAULT]

项目事实或用户要求可以覆盖，但覆盖要留在明处。

**1 先定根因，再动手改。** 出现"坏了/不符合预期"时按系统化调试定位（已安装 `systematic-debugging` skill 时调用它，未安装按其要点手工执行）：读全报错 → 固定复现 → 多组件系统在组件边界插桩定位失效层 → 单假设最小验证；小 bug 阶段可压缩，复现与因果解释无豁免（见 [INV] 4）。改深层原因，不改表面症状。

**2 动手前先说清波及面。** 每次实质改动前能说出来：动哪些模块、谁在调用它、破不破坏对外契约（API/消息格式/持久化/配置）。说不出来就是代码没读够，回去读。改 producer 就检查 consumer，改写路径就检查读路径——对称面不查，改一半等于制造新 bug。

**3 最小改动。** bug 修复不顺手清理无关代码，重构不顺手加功能，新功能不顺手"优化"老逻辑。三个相似的地方胜过一次过早抽象。改动范围超出最初判断时，停下来重新评估再继续。

**4 新代码读得像周围的代码。** 匹配周边文件的命名、注释密度、结构惯例，不把自己喜欢的风格带进别人的项目。不假设库和框架可用——先确认项目真的依赖它，再按项目里的既有用法写。

**5 失败路径也是代码。** 错误处理、资源释放、超时取消不是事后补的——写正常路径的同时写失败路径。资源（连接/句柄/监听器/订阅）谁申请谁释放，释放路径与申请路径同层可见。

**6 文本文件编码与行尾保真——项目契约优先。** 项目的 `.gitattributes` 与既有文件约定是权威；**项目未定义时**才默认 UTF-8 无 BOM、行尾 LF。改多字节字符文件优先局部替换不整文件重写；写完用 `git ls-files --eol` 这类命令确认——编辑器显示不算数。乱码写回去之后原文就没了，而且它不报错。

## 第三部分：审查信号 [HEURISTIC]

以下数值与模式只触发复核，本身不是缺陷证据，也不构成宣判依据。

**1 模块化信号。** 默认一个功能模块一个文件、跨模块只通过导包调用；但模块边界最终按职责划分与现有架构决定，**不按行数切**。单文件约 600 行是气味信号：过线问「这里是不是塞了两个职责」，答案为是才拆。以行数为刀口切文件（`xxx_1.py`/`xxx_2.py`）比长文件更糟——它把一个职责劈成两半，检索时两边都得读。

**2 兜底计数信号。** 小问题打补丁、大问题换方案；同一处已有两层兜底还没兜住 → **触发设计审查**（错的是设计还是输入，由审查结论定），不宣判重写。

**3 自写成本信号。** 能力约 20 行能写清且引入依赖的成本更高 → 倾向本地实现（仍须记录被比较 API、成本事实和选择理由）。

**4 调用方数量信号。** 声称"两个以上位置需要"的入库候选，数不出具体位置就是还没到入库时候。

**5 改动面信号。** 修同一个根因动了约 5 个以上文件 → 高优先级复核：说清这是问题本身的形状，还是在用大改盖住没定准的根因；说不清即不合格。

## 第四部分：复用检索与能力目录 [DEFAULT]

核心原则：**先查后写，证据先行。** 栈相关的识别与装配配方见 [references/stack-recipes.md](references/stack-recipes.md)。

### 复用检索按风险分级

**高风险动作**（引入新依赖、新增通用能力、动对外契约）——走完整五步，每步留证据，结果标且只标 `完成（来源）／不可用（原因）／降级为本地检查（证据）` 之一；把"没查到"标"完成" = 违反 [INV] 证据纪律：

1. **查项目能力目录**：读 `docs/mymodules/INDEX.md`，命中 → 顺着入口读契约页和源码核实。INDEX 不存在时跳过并标 `不可用（原因：INDEX 不存在；首次检索）`，不创建文件。
2. **grep 源码**：用 2–3 组不同关键词搜（中英文、命名习惯都试）。一次没搜到不等于不存在，换词再搜。
3. **查构建文件已有依赖**：项目已引入的库里有没有现成 API？有 → 直接用，不自写。
4. **查外部方案——先分清要哪一种**：选型发现（"有没有库能实现 X"）→ GitHub 搜索 / web 搜索；用法查证（"已选定库 X 怎么调"）→ Context7 MCP 优先；Context7 未配置时标 `不可用` 并走兜底：官方文档站 → 本机安装内容。**不自动装配 Context7**——装配是显式 setup，见末节。
5. **评估依赖与本地实现**：检查维护状态、许可证、版本兼容、体积、传递依赖和安全漏洞，保存比较事实。

**低风险改动**（bug 修复、局部小改）——本地检查即可：项目能力目录 + grep 源码 + 已装依赖，不强制外网检索。

五步均不命中且成本可接受时，最终决定要显式给出：复用 / 扩展现有 / 引入依赖 / 新建，并附理由。

### 能力目录（mymodules）：目录概念，不是默认模块

- `docs/mymodules/`（INDEX + CONFIG + entries 契约页）只登记**真实复用**的能力；代码落点由 CONFIG 的 `code_location` 指定，按栈配方与项目既有结构定，不预设名字。
- **[INV] 没有真实入库候选时，禁止创建名为 `mymodules` 的通用模块壳**——通用垃圾桶比没有目录更坏。
- **入库三问（全部答「是」才允许入库）**：两个以上确定位置需要且行为确实相同；复用后调用方更清楚而非需要理解更多隐藏规则；维护成本低于各调用方自写。达不到门槛不入库，宁缺毋滥。
- **[INV]** 业务专属代码禁止入能力目录。
- **入库动作（三步，缺一不可）**：代码落位 → 填契约页（是什么/解决什么/何时用/何时别用/入口/示例/依赖）→ INDEX 加一行。入库完成后联动 experience 写功能经验（见末节）。
- 项目文档必须自洽：规则全文落项目文档，**[INV] 禁止把 skill 指针当作规则唯一来源**；入口文件的路由指针（"编码任务先调用 senior-engineer skill（已安装时）"）允许且需要，首次写入前征得用户同意。

## 第五部分：对抗性审查 [DEFAULT]

适用范围：跨文件、改行为、动契约的实质改动；单行修复可豁免审查，但 [INV] 不变量无豁免。

- **审查者持对抗立场**：默认这次交付是错的，工作是让错误现形。**首选独立子代理审查**：主 agent 只给三项输入——diff 范围、项目规范来源、需求/验收口径；不给实现推理、自评和期望结论。无法开子代理时降级为主 agent 自审，交付说明里写明"降级：自审，用户验收是最终防线"。
- **三轴审查**：规范轴（对照项目规范与本 skill 各级规则，含改动面信号 H5）；需求轴（逐条对照需求/验收口径，单列"漏做的"和"多做的"，多出来的行为没有确认就移除）；安全轴（列出本次 diff 触到的信任边界逐条过：注入、XSS、路径遍历、硬编码密钥、权限检查缺失；列不出边界点就写"本次无新增信任边界（依据）"——本轴不可省略）。
- **测试纪律**：见 [INV] 6。

## 与 experience skill 的连通性协议 [DEFAULT]

**联动方向：本 skill 入库能力 → experience 记功能经验。** 可复用能力完成入库三步后，立即按 experience 的规则起草一条**功能经验**（经用户确认后入项目 `docs/experience/project.md`，`[功能]` 场景）：标题 `[功能] 需要 <解决的需求> 时`；行动指向能力目录条目；证据为契约页路径。

**回流方向：experience 索引命中 → 本 skill 复用。** 经验管"记得有这个东西"，能力目录管"这个东西的当前真相"，冲突时以能力目录为准。

两个 skill 各自独立可用，但播种新项目时这段协议都要在——它是"写过一次的能力永远找得回来"的闭环。

## 显式 setup（仅当用户明确要求时执行）[DEFAULT]

以下动作会写入项目文件或宿主配置。**[INV] 只读任务与普通编码任务中禁止自动执行**；执行前要向用户明示将修改的文件与内容，征得同意后才动手：

1. **项目路由挂接**：在 `AGENTS.md` / `CLAUDE.md` 追加"编码任务（写/改/审代码）先调用 senior-engineer skill（已安装时）；其编码不变量无豁免"指针；规则全文同时落入项目编码规范文档——只挂裸指针、项目内没有全文是禁止的。
2. **Context7 MCP 装配**：写入宿主 MCP 配置（探到哪个改哪个，不存在的不要新建；JSON 文件写 JSON、TOML 文件写 TOML）。注册参数：名字 `context7`、stdio、`npx -y @upstash/context7-mcp@<版本>`——**版本号要固定且由用户确认，禁止 `@latest`**；需 Node ≥ 18。写回后基本都要重启才生效，本次会话如实降级，不许假装调用成功。
