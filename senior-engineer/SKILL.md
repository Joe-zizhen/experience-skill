# senior-engineer — 编码行为、复用治理与对抗性审查

本 skill 回答一个问题：**高级工程师写代码时，有哪些不明说但都执行的规矩？** 它不编排流程，只约束编码行为本身。每条规则都要能判定违反——不可判定的规则等于没有规则。

分工：本 skill 管**编码时的一切**——规范、风格、模块体系、复用检索、审查；**experience** skill 管跨会话记忆（坑/入口/用户决策/功能经验）。两者接缝见末节。

## 第一部分：六条编码红线（通用，任何项目适用）

**1 模块化编程。** 一个功能模块一个文件；跨模块只通过导包调用，不伸手进别人的内部实现。出现反向依赖要么改设计要么记技术债，不许悄悄加。单文件 600 行是**气味阈值不是硬顶**：过线先问「这里是不是塞了两个职责」，是就按职责边界拆。**禁止以行数为刀口切文件**——`xxx_1.py`/`xxx_2.py` 把一个职责劈成两半，检索时两边都得读，比一个长文件更糟。

**2 兜底不许叠到第 3 层。** 小问题打补丁，大问题宁可重写也不要一直兜底。同一处已有两层兜底还没兜住，错的是设计不是输入——兜底层数可数，数出来 ≥3 就停手换重写。

**3 默认过滤必须在函数签名旁披露。** 读取类函数默认隐藏了数据（软删除、禁用、归档、时间窗），必须在签名旁写明「默认隐藏什么」「怎么取全量」。不披露的后果不是报错，是**静默少数据**——调用方拿到一个看起来正常的短列表，没人会去查。

**4 注释与 docstring 只描述实测成立的行为。** 写下「线程安全」「幂等」「自动重试」之前先有一次实测，拿不出实测就删掉那句。过期注释比没有注释更坏：它让下一个人跳过验证直接用。

**5 文本文件编码与行尾保真。** UTF-8 无 BOM；行尾由 `.gitattributes` 定，不靠编辑器。改多字节字符文件优先局部替换不整文件重写；写完用 `git ls-files --eol` 这类命令确认——编辑器显示不算数。乱码写回去之后原文就没了，而且它不报错。

**6 替代数据必须带来源标记，标记不许在层间丢失。** mock、假数据、降级返回值从产生那一刻就带上「这是替代数据」的标记，一路传到消费端，中间任何一层不许摘掉。不带标记的假数据跟真数据长得一模一样——上线那天字段对不上才发现。

## 第二部分：六条行为铁律（高级工程师的隐含工作方式）

**1 先定根因，再动手改。** 出现"坏了/不符合预期"时按系统化调试定位根因（已安装 `systematic-debugging` skill 时调用它，未安装按其要点手工执行）：读全报错 → 固定复现 → 多组件系统在组件边界插桩定位失效层 → 单假设最小验证；小 bug 阶段可压缩，复现与根因结论无豁免。**拿不出复现步骤的根因只是假说，禁止在没有根因结论前打补丁、加防御性判断、加重试**。补丁盖住的 bug 会换个形态再出现；改深层原因，不改表面症状。修同一处两次仍没好 → 停手，你的问题模型是错的，先质疑架构再动手。

**2 动手前先说清波及面。** 每次实质改动前能说出来：动哪些模块、谁在调用它、破不破坏对外契约（API/消息格式/持久化/配置）。说不出来就是代码没读够，回去读。改 producer 就检查 consumer，改写路径就检查读路径——对称面不查，改一半等于制造新 bug。

**3 最小改动。** bug 修复不顺手清理无关代码，重构不顺手加功能，新功能不顺手"优化"老逻辑。三个相似的地方胜过一次过早抽象。改动范围超出最初判断时，停下来重新评估再继续——大范围重写经常是在盖住一个没定准的局部问题。

**4 新代码读得像周围的代码。** 匹配周边文件的命名、注释密度、结构惯例，不把自己喜欢的风格带进别人的项目。不假设库和框架可用——先确认项目真的依赖它，再按项目里的既有用法写。

**5 交付物必须完整且已验证。** 不留占位符和"rest unchanged"式的半截活；每个结论有证据（命令亲手跑过、输出实际看过）。"应该能过"不是过。

**6 失败路径也是代码。** 错误处理、资源释放、超时取消不是事后补的——写正常路径的同时写失败路径。资源（连接/句柄/监听器/订阅）谁申请谁释放，释放路径与申请路径同层可见。

## 第三部分：复用检索与 mymodules 入库治理

核心原则：**先查后写，证据先行。** 栈相关的识别与装配配方见 [references/stack-recipes.md](references/stack-recipes.md)。

### 复用红线（不可违反）

1. **未检索，不动笔。** 任何新功能/工具/组件/封装，先走完「检索流程」并留下检索证据，才允许写新代码。
2. **禁止把官方库源码抄进来改。** 唯一例外是官方明确以 sample/codelab 发布的参考代码且保留许可证头。引入官方或第三方依赖前必须评估版本兼容、体积、许可证、维护状态和传递依赖并留证据；能力很小（约 20 行能写清）且依赖成本高于本地维护成本时允许自写，必须记录被比较 API、成本事实和选择理由。
3. **可复用代码不放 docs/。** `docs/mymodules/` 只放目录与契约文档；代码落点由 `CONFIG.md` 的 `code_location` 指定。
4. **业务专属代码禁止入 mymodules。** 只与一个业务场景绑定的代码，留在业务代码处。
5. **达不到入库门槛不入库。** 宁缺毋滥，目录失去可信度就等于没有目录。
6. **项目文档必须自洽，禁止引用 skill 自身。** 写入项目的任何文档不得出现"见 senior-engineer skill"字样或 skill 的安装路径——规则全文必须写在项目文档内。仓库是权威；skill 只是执行器，在其他机器上可能不存在。

### 检索流程（每次写代码前，按顺序）

每步都要留下证据，结果必须逐步标为且只能标为 `完成（来源）／不可用（原因）／降级为本地检查（证据）` 之一。`不可用` 与 `降级为本地检查` 是诚实的终止状态，不得改写成"已完成"。

1. **查项目索引**：读 `docs/mymodules/INDEX.md`，命中 → 顺着入口读契约页和源码核实，复用或扩展。INDEX 不存在时跳过并标 `不可用（原因：INDEX 不存在；首次检索）`，不创建文件。
2. **grep 源码**：用 2–3 组不同关键词搜（中英文、命名习惯都要试，如 `back`/`返回`/`toolbar`/`navigation`）。一次没搜到不等于不存在，换词再搜。找到候选 → 评估契约是否匹配。
3. **查构建文件已有依赖**（`build.gradle` / `package.json` / `go.mod` 等）：项目已引入的库里有没有现成 API？有 → 直接用，不许自己写。
4. **查外部方案——先分清你要的是哪一种**：

   - **选型发现**（"有没有库/现成方案能实现功能 X"）→ **用 GitHub 搜索 / web 搜索**（搜仓库、awesome 列表、社区对比讨论）。**Context7 不适用于此**——它只收录已被索引库的文档，回答不了"有没有"。
   - **用法查证**（"已选定库 X，查它的 API 怎么调"）→ **Context7 MCP 优先**（工具列表里有 `resolve-library-id` 时）：调 `resolve-library-id` 拿 library ID，再调 `get-library-docs` 取最新文档，标 `完成（Context7：<library-id>）`。

   Context7 未配置时的装配：优先用当前 agent 自己的 MCP 注册命令（`claude mcp add` / `codex mcp add` 等，先 `which` 核实存在）；没有注册命令才探测配置文件手改（探到哪个改哪个，不存在的不要新建；JSON 文件写 JSON、TOML 文件写 TOML，格式跟着文件走）：Claude Code `~/.claude.json`（`mcpServers`）、Codex `~/.codex/config.toml`（`[mcp_servers.context7]`）、Cursor `~/.cursor/mcp.json`、Windsurf `~/.codeium/windsurf/mcp_config.json`、Gemini CLI `~/.gemini/settings.json`。注册参数统一：名字 `context7`、stdio、`npx -y @upstash/context7-mcp@latest`（需 Node ≥ 18）。都探不到就问用户一次并把答案钉进 `docs/mymodules/CONFIG.md` 的 `mcp_config_path`。写回后基本都要重启才生效——本次会话如实降级，不许假装调用成功。

   **兜底顺序**（仅在已装配或装配做不到时）：官方文档站 → 本机安装内容。官方站结果只作补充。装配做不到的合法情形只有三种：没有 Node ≥ 18、配置文件不可写、用户明确拒绝装。

   **一律禁止**：把"没查到"标 `完成`；把本机存在性检查当作文档检查；用 Context7 做选型发现。
5. **评估依赖与本地实现**：对官方/第三方候选检查维护状态、许可证、版本兼容、体积、传递依赖和安全漏洞；能力约 20 行能写清且依赖成本高时可选择本地实现。保存比较事实，确认团队愿意长期维护才引入依赖。

五步均取得上述状态后，没有契约匹配且成本可接受的复用/依赖方案，才允许自己写。最终决定必须显式给出：复用 / 扩展现有 / 引入依赖 / 新建，并附理由。

### 首次装配（懒装配）

项目中还没有 `docs/mymodules/CONFIG.md` 时，首次触发只执行上方五步检索，不创建任何治理文件。直到实现后出现真实入库候选且入库三问首次全过，才执行一次装配：

1. 读仓库根目录的 manifest 信号（`settings.gradle(.kts)` / `package.json` / `go.mod` 等），按 [references/stack-recipes.md](references/stack-recipes.md) 判定技术栈。
2. **先验证现成落点**：找到 `common|shared|core|base|util(s)|lib` 候选后，用 grep 统计其导入/调用位置并保存证据；现有内容被两个以上独立位置真实复用且职责边界匹配时，才把候选作为 `code_location`。否则按领域/基础设施边界放置；仍有两个以上合理答案时只问用户一次并钉进 CONFIG。
3. 需要新建时：按对应栈配方创建 `code_location` 隔离单元、完成接线，并运行配方里的验证命令证明接线通了。
4. 写入 `docs/mymodules/CONFIG.md`、`INDEX.md` 和 `entries/_template.md`；同一流程必须继续登记当前真实候选，不得留下空壳。之后所有会话直接读钉子，不再重新探测。
5. AGENTS.md 有则续写无则新建：登记「新增通用能力前必读 docs/mymodules/INDEX.md 与 CONFIG.md」。

### 入库流程（实现完成后）

**入库三问（全部答「是」才允许入库）：**

1. 这段逻辑是否在两个以上确定的位置需要，且行为确实相同？
2. 复用后调用方会更清楚，还是需要理解更多隐藏规则？（前者才过）
3. 它的维护成本是否低于各调用方自己写几十行清晰代码？（是才过）

**入库动作（三步，缺一不可）：**

1. 代码放到 `CONFIG.md` 指定的 `code_location`。
2. 复制 `entries/_template.md` 为 `entries/<能力名>.md`，填完整契约页：是什么、解决什么需求、什么时候用、什么时候别用、入口路径、用法示例、依赖。
3. `INDEX.md` 目录表加一行：能力名 | 入口路径 | 一句话用途 | 契约页链接。

**入库完成后，联动 experience 写功能经验**——见末节连通性协议。

## 第四部分：对抗性审查（实质改动交付前必做）

适用范围：跨文件、改行为、动契约的实质改动；单行修复可豁免审查，但红线无豁免。

**审查者持对抗立场**：默认这次交付是错的，你的工作是让错误现形，不是确认它对。**首选独立子代理审查**：主 agent 只给三项输入——diff 范围、项目规范来源、需求/验收口径；**不给实现推理、自评和期望结论**（给了这些，审查就变成了复读）。无法开子代理时降级为主 agent 自审，必须在交付说明写明"降级：自审，用户验收是最终防线"。有限度的审查好过跳过审查。

**三轴审查**：

- **规范轴**：对照项目规范与六条红线；查命名不清、重复代码、职责混杂、隐藏耦合、散弹式修改（一处改动导致处处改）。**修同一个根因动了 5 个以上文件 → 高优先级问题**：说清这是问题本身的形状，还是在用大改盖住没定准的根因；说不清即不合格。
- **需求轴**：逐条对照需求/验收口径，单列"漏做的"和"多做的"；每个变更必须映射到需求项，多出来的行为没有确认就移除。
- **安全轴**：列出本次 diff 触到的信任边界（外部输入入口、权限判定点、密钥与敏感数据经手处），逐条过：注入、XSS、路径遍历、硬编码密钥、权限检查缺失。列不出边界点就写"本次无新增信任边界（依据）"——不许省略本轴。

**测试纪律（死规矩）**：

- **红绿反验**：证明测试能失败——故意改一个期望或输入，确认测试变红，再改回来。没红过的测试不算测试。
- **禁止自证测试**：期望值不许用被测代码的同一算法/helper 计算；期望只能来自独立样例、固定 fixture、合同或独立 oracle。
- **每道防线都要证明它能拦住**：新增的每个校验/过滤/权限判断/边界守卫，逐个喂一个本该被它拦下的输入，观察它真的拦下了。做不到就删掉或改成能触发的写法——**恒真守卫比没有守卫更坏**：它让所有人都以为这里有防线。守卫的注释只许描述实测能拦下的范围。
- 不许用 skip、删测试、放宽断言、mock 被测对象、`|| true`、降阈值制造绿灯。

## 与 experience skill 的连通性协议

**联动方向：本 skill 入库模块 → experience 记功能经验。**

可复用能力完成 mymodules 入库三步后，立即按 experience 的规则起草一条**功能经验**（经用户确认后入项目 `docs/experience/project.md`，`[功能]` 场景）：

- 标题：`[功能] 需要 <解决的需求> 时`
- 行动：当需要实现 <需求> 时，复用 `<code_location>` 的 <能力名>（mymodules 已登记），不要新写
- 证据：mymodules 契约页路径
- 记录日期：`date +%F` 取系统时间

**回流方向：experience 索引命中 → 本 skill 复用。** 未来任务在 experience 索引命中功能经验时，顺着指针读 mymodules 契约页核实后再复用——经验管"记得有这个东西"，mymodules 管"这个东西的当前真相"，冲突时以 mymodules 目录为准。

两个 skill 各自独立可用，但播种新项目时这段协议都要在——它是"写过一次的能力永远找得回来"的闭环。

## 项目路由播种（首次在某项目被调用时必做）

description 匹配是概率性的，项目入口文件的路由是结构性的——本 skill 自己负责把后者挂上：

1. 首次在某项目被调用时，检查项目入口文件（`AGENTS.md` / `CLAUDE.md`）是否已有指向本 skill 的编码任务路由。
2. 没有则追加一条："编码任务（写/改/审代码）先调用 senior-engineer skill（已安装时）；其编码红线无豁免。"两个文件都在就两个都写。
3. **路由只写指针，不写规则全文**——规则以本 skill 为唯一权威；skill 未安装的环境里指针自然降级（按普通编码流程走），不阻断、不报错。
4. 项目没有入口文件时，告知用户需要手动挂路由，不替他编造项目文档。
5. 写入后一句话告知用户已挂接。
