# Myskills — 个人 AI agent skill 集合

一套让 AI agent「想得清、记得住、写得正、修得准」的闭环工具箱。六个 skill 各管一段，合起来覆盖从「脑子里一个模糊想法」到「交付、验收、沉淀经验」的全流程。

## 全景：它们怎么连成一条流水线

```
你的想法
  ↓
pm            需求入口：反问、评审、出任务书
  ↓
first-principle-v2   重大/难逆的技术决策（按需）
  ↓
senior-engineer      编码执行：红线、铁律、复用、审查
  ↓
systematic-debugging 修 bug（按需）｜ 5w-ledger-v1-2 事故复盘（按需）
  ↓
experience    经验沉淀：坑、入口、决策、功能全部记下来
  ↓
下一个任务自动避坑 ← 闭环
```

## 速览：什么情况用哪个

| 你的情况 | 用哪个 |
| --- | --- |
| 「我有个想法 / 帮我写个 PRD / 写个任务书给 agent」 | `pm` |
| 要写、改、审任何代码 | `senior-engineer` |
| 出了 bug、测试挂了、行为不对 | `systematic-debugging`（senior-engineer 铁律 1 已自动联动） |
| 高危事故、复盘、交接、多因交织的故障 | `5w-ledger-v1-2` |
| 重大、难逆、代价高的技术/架构决策 | `first-principle-v2` |
| 任何任务（每次任务开头自动读经验库，防重复踩坑） | `experience` |

## 1. pm — 需求入口：你出想法，它出需求与任务书

**解决的痛点（四个，全是真的）：**

- 想法直接开工，执行完才发现方向就错了——下游一切努力白费。
- 跟 AI 讨论需求时它钻牛角尖：第一个问题问技术栈，后面五六个全围着技术栈，功能、边界、验收一个不问。
- AI 满嘴术语英文，你听不懂，还得一个一个追着问。
- 需求用散文写给执行 agent，它自由发挥，做出来的不是你要的。

**是什么：** 扮演产品经理 + 项目经理。你是领导（出想法、拍板），它是 PM（调研、反问、写文档、验收），把模糊的想法逐步挤成三份工件：概念版（你拍板用，一页内）、落地规格（验收标准+非目标+状态穷尽）、任务书（直接投给执行 agent，2664 字符级别的可执行信封）。

**核心机制：**

- **三型分流**：模糊痛点 → 引导访谈；成形想法 → 挑战攻防；明确需求 → 直通规格。它会先喊出判定，你可一票改判。
- **宏观六维防钻牛角尖**：目标与用户 / 功能范围 / 数据与状态 / 边界与非目标 / 技术约束 / 验收标准——六维全覆盖前禁止深挖，同一维度连续提问 ≤2 个。
- **提问纪律**：调研先行（自己能查的一律不问）；每轮 ≤5 问、带选项和推荐；**替拍负面清单**——数据位置、删除语义、花钱、权限安全、破坏现有数据，这五类决策不许它替你拍，必须问你。
- **方向关卡**：展开细节前，对概念版做一次「双向钢人」攻防（重述→支持/反对最强论证→真正分歧→只问一个最关键问题），你拍板才许继续。
- **语言红线**：对话说人话（术语首次出现括号给半句人话，选型给人话利弊+推荐）；文档随便专业（给 agent 看的，能完成为唯一标准）。
- **任务书机制**：一个目标一次交付、Goal 模式 ≤4000 字符硬顶、开工先读路径、不许重复造轮子、死接口点名、防五种死法（作弊达标/幻觉命令/失忆/一条道走到黑/静默事故）、明卷+暗卷验收。

**怎么用：** 跟 agent 说「我有个想法」「帮我写个 PRD」「写个任务书给 agent」即触发。产物落在项目的 `docs/project-milestones/requirements/<主题>/`。

**边界：** 不做技术方案深设计（重大技术分叉移交 first-principle-v2）；不修 bug；死因自带——连续 3 次「执行完才发现方向错」降级为被动模板，2 个月零使用删除。

## 2. senior-engineer — 编码行为：让每一行按高工标准写

**解决的痛点：** AI 打补丁式修复（哪儿坏糊哪儿）、不追根因、不管全局、重复造轮子、自审自夸。

**是什么：** 一套可判定的编码行为准则——每条规则都能数出违反，不依赖「自觉变好」。

**核心机制：**

- **六条编码红线**（违反即不合格）：模块化（一个职责一个文件）；兜底不许叠到第 3 层；默认过滤必须在函数签名旁披露；注释只描述实测成立的行为；文本编码与行尾保真；替代数据（mock/假数据）必须带来源标记且层间不丢。
- **六条行为铁律**：先定根因再动手（拿不出复现步骤的根因只是假说，修 bug 走 systematic-debugging）；动手前说清波及面；最小改动；新代码读得像周围的代码；交付必须完整且已验证；失败路径也是代码。
- **复用检索五步**：写任何新能力前，查项目 mymodules 目录 → grep 源码 → 已装依赖 → 官方文档（Context7）→ 评估自写；每步留证据，「查不到」不许写成「完成」。实现出可复用能力时执行 mymodules 入库三问+三步。
- **对抗性审查**：实质改动交付前必做；首选独立子代理（只给 diff、规范、验收口径三样，不给实现推理——防止审查变复读）；三轴（规范/需求/安全）；测试死规矩（红绿反验、禁自证测试、每道防线必须喂坏输入证明能拦）。

**怎么用：** 任何写/改/审代码的任务开始时调用。项目里的 `CODING.md` 有这套规则的项目内落地全文——skill 不在场时项目照样自洽。

**边界：** 管编码时的一切，不管需求对不对（那是 pm）、不管跨会话记忆（那是 experience）。

## 3. experience — 外置大脑：让代价只付一次

**解决的痛点：** agent 的记忆 = 当前会话，关掉就清零——上次掉的坑下次再掉，你定过的约定全不记得。

**是什么：** 跨会话经验系统。核心认知一句话：**存储不是经验，检索才是**——所以它的大头不在「写」，而在「决策点之前把相关经验灌进上下文」。

**核心机制：**

- **门禁**：每次任务开始必读项目 `docs/experience/INDEX.md`（一屏以内），最终回答首行输出 `[经验门禁] 命中 N 条 / 无命中`——读没读一眼可查；SessionStart hook 再自动注入一次（结构性强制）。
- **检索三通道**：逐行匹配索引行；grep 全文兜底；**决策点重扫**（任务性质转变时重扫对应场景行）。
- **入库四问**（缺一不收）：会重现、重导有代价、改变行动、写得出死因。条目一律祈使句，标题 = 触发条件 + 关键词簇（含 1–2 个「任务时说法」）。**入库、删除、冷藏全部要你确认**，禁止静默写。
- **保鲜**：每条带死因；每天首次 git pull 后自清洁（锚点检查→死因核对）；与代码冲突时代码赢，标「疑似失效」走人工裁决。
- **规模**：永不因未命中淘汰（低频高价值条目正是要保的）；≤150 条全平铺，超过转两阶段；死场景进冷藏区，grep 可达。

**怎么用：** 什么都不用做——门禁自动生效。踩坑超过约 10 分钟、发现难找的入口、外部系统行为与文档不符、被你第二次纠正同一事实时，agent 会当场起草条目请你确认。

**边界：** 管记忆不管方法论（行为问题归 senior-engineer）。系统自己也带死因：连续零命中会逐级降级直至归档——它与条目同权，说不出死因的不收，定了死因的就执行。

## 4. systematic-debugging — 修 bug 的方法论

**解决的痛点：** 随机乱试（「改改这个看看」）、一次糊多个改动、猜根因、同一个地方修了三次还在坏。

**是什么：** 一条铁律「**没有找到根因之前，禁止任何修复**」+ 四阶段流程。

**核心机制：**

- **阶段 1 根因调查**：读全报错（别跳）；固定复现（触发不了就收集更多数据，不许猜）；查最近变更；多组件系统在组件边界插桩、跑一次定位失效层；数据流回溯到源头。
- **阶段 2 模式分析**：找代码库里能正常工作的相似实现，逐条列差异。
- **阶段 3 假设验证**：一次只一个假设、最小改动验证；不行就换新假设，不许在旧补丁上叠补丁。
- **阶段 4 实施**：先写能复现的失败测试，一次只改一处，验证全局无回归。
- **3 次失败 → 停下来质疑架构**（不是换第 4 个补丁）；红旗清单（「快速修一下」「应该是 X」这类念头一出现就停）。
- 支撑技术文件：`root-cause-tracing.md`（回溯定位）、`defense-in-depth.md`（多层校验）、`condition-based-waiting.md`（条件等待替代拍脑袋超时）、`find-polluter.sh`（查污染源）。

**怎么用：** 出 bug 时用。senior-engineer 的铁律 1 已联动——任何「坏了/不符合预期」都会走到这里。

**边界：** 管技术诊断；事故级的可审计因果合成归 5w-ledger-v1-2。

## 5. 5w-ledger-v1-2 — 事故级根因分析（证据台账版五个为什么）

**解决的痛点：** 重大故障后说不清到底为什么、复盘靠拍脑袋、多个原因交织时被简化成一个错误故事、交接给别人时因果链经不起追问。

**是什么：** 证据驱动的 Five Whys。每个因果环节必须先过**证据准入台账**（ADMIT / REJECT / UNKNOWN），最终报告只能用 ADMIT 过的证据搭出来——因果链每一环都可审计。

**核心机制：** 症状/触发/直接原因/促成原因/根因/控制缺口严格分类；多因交织时必须给出**最小充分因果集**并区分「边界内可改」与「边界条件」；时间窗故障先建时间线，因必须先于果；置信度分级（confirmed/probable/hypothesis）且全文不许超过最弱一环；输出固定两段（台账 + 最终 RCA）。

**怎么用：** 高危事故、跨时间窗故障、多因交织、审计复盘、交接场景。**日常局部 bug 不要用它**——那是 systematic-debugging 的地盘，这个 skill 自己的规矩就禁止拿它杀小鸡。

## 6. first-principle-v2 — 重大决策的第一性原理设计

**解决的痛点：** 凭惯性抄方案（「上次这么干的」「大家都这么干」）、重大难逆决策拍脑袋、在错误的假设上盖楼。

**是什么：** 从基础事实出发推导最简正解的设计流程。默认产出是设计/决策，不是代码。

**核心机制：** 一句话定义目标结果 → 决策输入四分（实测事实 / 需求 / 约束 / 假设——约束再分「设计约束可挑战」与「增生约束当边界」）→ 挑战每个没证据的假设 → 分解到不可再分 → 从验证过的事实重建最简设计 → 旧组件先过「补丁堆阈值」（该重写还是该 incremental）→ 候选对比（含「不新增组件」选项）→ 每步独立可验证可回滚的迁移路径 → 盲点扫描 → 验证计划（最便宜的能推翻决策的假设最先测）。

**怎么用：** 重大、难逆、假设未决的决策：架构选型、重写还是修补、引入重依赖、5W 复盘后的修复方案设计。常规任务不要过度调用（它自己的规矩）。

cp -r ~/skills-collection/experience ~/.agents/skills/
cp -r ~/skills-collection/senior-engineer ~/.agents/skills/
cp -r ~/skills-collection/systematic-debugging ~/.agents/skills/
cp -r ~/skills-collection/5w-ledger-v1-2 ~/.agents/skills/

cp -r ~/skills-collection/pm ~/.agents/skills/

Claude Code 则拷到 `~/.claude/skills/`。**装完重启宿主**——技能清单是会话启动时加载的缓存，不重启看不见新 skill。

- 各项目里的 `docs/experience/`（项目经验）不进本仓，随项目自己的 git 走。
