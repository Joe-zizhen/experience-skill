# First Principle Thinking

Use first-principle thinking to design forward from foundational facts instead of copying existing patterns. The default output is a design or decision, not an implementation. Strip away assumptions, identify irreducible truths and constraints, then derive the simplest solution that directly satisfies them. The simplest correct solution minimizes total lifecycle complexity, not merely code size or component count.

## Workflow

1. Define the target outcome in one sentence: what must become observably true for the user or system, how success will be judged, and the relevant time horizon when it matters. Do not embed a preferred implementation unless it is a real constraint.
2. Separate decision inputs:
   - Observed facts: directly inspected, reliably measured, or verified current-state evidence.
   - Required outcomes: normative conditions the user, business, or system needs; a user statement is a requirement, preference, or claim, not automatically an observed fact.
   - Constraints: physics, platform and API rules, regulation, time, cost, compatibility, security, scale, UX, maintainability, and team capability. Mark hard constraints and soft preferences distinctly.
   - Assumptions: unverified claims, forecasts, inherited conventions, guesses, analogies, or "we usually do it this way".
   **Classify each constraint into one of two categories and treat them differently:**
   - **Design constraints**: intentional choices (architecture patterns, framework selections, API contracts, data schemas) — these can be challenged and re-evaluated against first principles. Their authority derives from the decision that created them; if that decision's rationale no longer holds, the constraint may be overturned.
   - **Accretion constraints**: emergent facts from system evolution (compatibility contracts exposed to external consumers, implicit data consistency dependencies, regulatory obligations, irreversible data migrations) — these cannot be changed within the scope of the current design without an independent migration project. Accept them as boundary conditions for this design but do not replicate them into new components. **An accretion constraint binds the compatibility *surface* (e.g., the test-observation boundary, the API contract signature), not the internal design of new components built behind that surface.** Changing an accretion constraint requires a separate decision with its own cost/risk assessment.
   If classification is uncertain — the item's mutability or authority cannot be established from available evidence — do not default to accretion. Instead, flag it as an unresolved classification, design the most reversible viable path that does not depend on the classification being right, and treat resolving it as a staged decision gate (Step 7).
   **External date-locked constraints** (regulatory deadlines, contract expiry, certification clocks, attrition dates) are hard constraints with a fixed calendar date. When the design window contains multiple such dates, compute the timeline arithmetic before accepting any stated delivery target — the most constraining external date sets the true deadline. A stated delivery target that is arithmetically incompatible with the external date chain is a design constraint, not a hard deadline: challenge it as such.
   **Team capability** (expertise distribution, institutional knowledge, team size, turnover) is a soft feasibility input, not a design boundary. It does not eliminate candidates from consideration but adjusts execution: reduce migration step size so each step is independently completable by the available expertise; increase documentation and handoff checkpoints in proportion to knowledge risk; when a candidate requires capability the team lacks, treat the gap as a staged learning gate (spike, consultant, pair-programming) rather than a hard veto — unless the learning window exceeds the design's time constraint. When capability is carried by specific individuals with fixed departure dates, the departure date itself is a hard accretion constraint on the schedule: the knowledge must be captured or the dependency removed before that date, independent of whether the capability gap can be learned by others.
3. Challenge every decision-shaping assumption and every claimed constraint whose authority, necessity, or factual basis is not established. Ask what evidence supports it, whether it is actually necessary, and what changes if it is removed or reversed. For design constraints, treat them as challengeable — and for each challenged design constraint, identify the decision-owner with override authority and the minimum evidence that would reopen it. If the owner or evidence threshold is unknown, resolving them becomes a staged decision gate (Step 7). For accretion constraints, document why they bind the current design rather than expending effort to challenge them. Treat a challenged constraint as hard only when verified; otherwise retain it as an assumption or preference, or reject it.
4. Decompose the problem into needs, capabilities, and invariants until the remaining elements are basic and hard to dispute. Stop when further decomposition would not change the candidate designs, their ranking, or the validation plan. **Before stopping, verify each decomposed need names a capability the system provides, not a restatement of a required outcome. "Works offline" is a requirement; "read and write data while offline, tracking which changes have not yet been synchronized" is a capability. If any need is a verbatim restatement of a constraint or outcome, decompose one level deeper.**
5. **Verify observed-fact consistency before rebuilding: scan the alternatives considered against the observed facts listed in step 2. Any alternative rejected against a factual claim must not contradict an observed fact that was listed as verified. If a listed fact and a rejection reason conflict, resolve the conflict before proceeding — either the fact is wrong (downgrade it to an assumption), the rejection is wrong (reconsider the alternative), or the fact doesn't apply to the rejection's scope (narrow the rejection).** Then rebuild from those elements: derive the smallest design that satisfies the required outcomes and constraints with the least total lifecycle complexity. Include security, reliability, observability, migration, rollback, or maintainability only in proportion to material risk. Close each material invariant whose violation would make the design incorrect by naming its authoritative owner or state, enforcement or commit boundary, failure behavior, and recovery or reconciliation path; apply only the parts relevant to the decision.
6. **For brownfield components that have an existing implementation, evaluate whether accumulated patches have crossed the rewrite threshold before planning migration.** If the affected component is new or greenfield (no existing implementation), skip this evaluation and proceed directly to Step 7. For components with existing code, apply this gate:

   **Gate: patch-pile threshold.** Has the current implementation accumulated divergent copies of the same logic that have already drifted apart and would require coordinated changes to keep in sync, or special-case branches that route around the core rule? If so, estimate whether untangling them incrementally costs more than a clean rewrite. The signal is *drift* (copies that have diverged and will continue to diverge with each future change) and *coupling* (a change at one site requires coordinated changes at others), not count alone. The *affected component* is the minimal unit owning the defect — scope the rewrite to that unit, and reuse stable pieces (APIs, contracts, data schemas, external Activity Intent contracts) rather than rewriting them. Hard constraints from Step 2 short-circuit the gate: if a full-app rewrite is forbidden, the gate evaluates only component-scoped rewrites.

   **If the gate fires (rewrite justified):** carry the rewritten design into Step 7 as a named candidate alongside the incremental and no-new-component options. Apply the same four-part discipline to the rewrite path:
   - Precondition: what must be true before the rewrite starts.
   - Change scope: the minimal affected component being replaced, preserving stable contracts and hard constraints.
   - Rollback: how to revert the rewrite independently (if unrevertable, label it as an irreversible decision point and assess the risk).
   - Validation signal: the observable metric, test, or behavior that confirms the rewrite succeeded.

   **If the gate does not fire:** when the change is localized and touches no existing consumers, state, data, or contracts, state that no migration path is needed and why in one sentence — skip the decomposition below. Otherwise, decompose the incremental migration into a sequence of independent, verifiable intermediate states. Each state must keep the system operational and pass existing tests. For each migration step, define:
   - Precondition: what must be true before this step starts.
   - Change scope: what code, config, data, or infrastructure changes in this step.
   - Rollback: how to revert this step independently (if a step cannot be rolled back, label it as an irreversible decision point and assess the risk).
   - Validation signal: the observable metric, test, or behavior that confirms the step succeeded.
   If any step cannot be made independently verifiable or reversible, stop and reconsider whether the target architecture can be reached through a different sequence, or whether the risk of that step is acceptable. When multiple migration steps have no coupling between them — different components, different teams, no shared state or contract — they may be pipelined in parallel rather than sequenced. Name the coupling that prevents parallelism; if none exists, state that the steps are independent and may overlap in time.
7. Compare against current and conventional approaches only after deriving the baseline. When the core needs involve overload, capacity, outage or cascading-failure mechanics, or dormant-defect shapes, run one bounded pattern-recruitment pass before finalizing candidates: first state the semantics of the data (state vs event, ordered vs unordered, authoritative vs cacheable) and the second-order dynamics (how clients, users, and retries respond to the failure), then ask which known engineering pattern classes address this failure shape (for example conflation, backoff/jitter, backpressure, freeze windows, or evidence-gated decision records) and import them as candidates. Imported patterns are hypotheses entering validation, not conclusions: each must map to an observed mechanism in the evidence and earn its complexity like any other candidate. Degradation of quality metrics without those shapes does not trigger the pass; when no pattern applies, state none and move on. When the request names a technology or architecture, first derive a technology-neutral baseline and a no-new-component option; retain the named choice only if it measurably earns its complexity. Keep conventions that earn their place through domain knowledge, integration value, or reduced risk; discard those that do not. Generate multiple candidates only when material uncertainty or tradeoffs remain, and do not manufacture weak alternatives. Eliminate candidates that violate hard constraints or are dominated, then select the current course. Under material uncertainty, choose the most reversible viable course and turn unresolved evidence into a staged decision gate; do not use "more research" as a substitute for a decision when a bounded current choice is possible.
8. Explain why the solution is not more complex: map each included element to a required outcome, constraint, or material risk, and name the features, abstractions, or flexibility intentionally excluded.
9. Define validation: tests, prototypes, measurements, user checks, acceptance criteria, and falsification criteria. Test the cheapest decision-changing assumption early and the highest-risk assumption before irreversible investment. For each material gate, state the hypothesis, cheapest discriminating test, pass or fail threshold when measurable, action on success, and fallback on failure. State whether an unresolved fact blocks the overall decision or only a later stage, and what evidence would reverse the decision.
10. Run one blind-spot pass before finalizing: ask "What is the biggest thing I may be missing or failing to notice in the current situation?" Check for a missing fact, constraint, stakeholder, assumption, or second-order effect. If this reveals a material issue, revise the design once. Stop when the next concern is speculative, low-impact, or not actionable.
11. State the implementation boundary and next action. Stop at design when execution is not authorized, naming any required approval or input. When it is authorized, complete the design checkpoint before continuing.

## Conditional Checks

- For technology choices, verify current official or primary recommendations, versions, maintenance status, security posture, compatibility, and ecosystem maturity. If verification is unavailable, keep the claim as an assumption. Newer is not automatically better.
- For costly, high-risk, or hard-to-reverse decisions, examine failure modes, reversibility, migration and rollback, operational ownership, and staged validation gates.
- For a 5W handoff, consume the desired invariant, causal mechanism, problem structure characterization, evidence and confidence, relevant control gaps, and unknowns. Treat `probable` or `hypothesis` causes as assumptions to validate before irreversible design. Derive the design from the handoff; do not accept a diagnosis-stage solution by default. When the materials the handoff cites remain accessible — the supplied case narrative, if any, and any reachable system evidence — verify the handoff's load-bearing facts, reconciliations, and stated checks against them before any irreversible design step; a handoff claim that fails verification degrades to an unverified assumption. This is targeted verification of designated claims, not re-diagnosis. A reconciliation or stated check passes verification only when its premise is itself stated in the materials or independently observed; a plausible but unstated premise fails verification. In a closed narrative, verification means checking claims against the supplied narrative itself, not demanding evidence that does not exist.

## Guardrails

- Do not use first principles as an excuse to ignore proven constraints or domain knowledge.
- Do not over-decompose routine tasks unless explicitly invoked.
- Do not implement by default; follow the implementation boundary established in the workflow.
- Ask clarifying questions when a foundational fact is missing and guessing would change the solution.
- Prefer reversible decisions under material uncertainty.
- State uncertainty directly; do not hide missing evidence behind precise-looking scores or a polished narrative.
- Preserve the existing codebase style and contracts unless a first-principle argument clearly justifies changing them.
- Exclude speculative extensibility, premature abstraction, and features that do not serve a required outcome or mitigate a material risk.
- Maintain decision density: include a fact, decomposition, alternative, or check only when it changes the selected course, its boundary, a material risk, or the validation order. Do not restate the input or fill output sections with repeated reasoning.

## Engineering Chain

- 5W answers: what is the real problem?
- first-principle answers: from that problem, what is the simplest correct solution?
- Implementation is a separate reasoning stage; authorization already present in the current request is sufficient.

## Output Shape

Provide:

- Desired outcome
- Observed facts, required outcomes, and constraints (with design vs accretion classification)
- Current technology facts, if relevant
- Decision-shaping assumptions challenged and their status, if any
- Derived baseline and alternatives when material
- Selected solution and why it is not more complex
- **Incremental migration path** — when the change touches existing consumers, state, data, or contracts. Sequence of independently verifiable steps with preconditions, change scope, rollback, and validation signal per step; label any irreversible decision points. For a localized change with no consumer or state impact, state that no migration path is needed and why in one sentence.
- Blind-spot check
- Tradeoffs and reversibility
- Validation plan and decision-reversal conditions
- Implementation boundary / next action

For a small decision, combine sections while preserving decisive facts or constraints, material challenged assumptions, derivation, exclusions, and validation. Add migration detail only when risk justifies it. For greenfield designs, skip the migration path.
